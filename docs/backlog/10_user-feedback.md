# 10. ユーザーフィードバック・機能拡張アイデア

## 概要

ユーザーから寄せられた UI/UX 改善要望、機能追加アイデア、および運用上の考慮事項を記録したバックログ。
本リポジトリ（`sf-markdown-editor`）本体の改善要望に加え、課題管理組織（`hk.issue` 等）との連携アイデアを含む。

> 元は `sf-gantt-lwc` の `docs/backlog/10_user-feedback.md` に置かれていたが、内容がすべて `sf-markdown-editor`（`markdownChecklistPanel` / `markdownTaskPreview` / `markdownEditor`）に対するフィードバックであったため、本リポジトリへ移動した（2026-08-19）。

## フィードバック一覧と検討内容

### 1. チェックリスト内容とタスク作成エリアの列分け（表示ゆれ防止）✅ 対応済み（2026-08-19）

- **対応内容**: `markdownChecklistPanel.css` の `.md-checklist-row` を `display: flex` から `display: grid`（`grid-template-columns: minmax(8rem, 1fr) auto`）に変更し、チェックリスト内容（`.md-checklist-row-content`）とタスク作成エリア（`.md-checklist-row-actions`）を明確に2カラムへ分離した。内容列のテキストは `overflow: hidden; text-overflow: ellipsis; white-space: nowrap;` で省略表示し、`title` 属性で全文をツールチップ表示する。作成エリア列自体は幅が変わらないため、テキスト長による位置ズレ（Layout Shift）は発生しない。
- **ユーザーの声**:
  > 「Check リスト内容とタスク作成 エリアの列分けがされれば、内容の文字数による、表示ゆれが少なくなるのではと思いました。」
- **課題・背景**:
  - `markdownChecklistPanel` のチェックリスト表示エリアと、Task 作成用のアクション・入力エリアが同一行または可変幅で配置されている場合、テキストの文字数やフォントレンダリングによって幅が伸縮し、レイアウトのガタつき・表示ゆれ（Layout Shift）が発生しやすい。
  - 特に多言語表示や長いチェックボックス項目名の入力時に、ボタンや入力フォームの位置がズレて操作性が低下する。
- **改善案・対応方針**:
  - **グリッド／カラム分離**: チェックリスト表示エリアと Task 作成エリアを明確に列（カラム）として分離し、固定幅または `grid-template-columns` による比率配分を適用。
  - **テキスト省略・折り返し制御**: チェックリスト項目が長い場合でも、領域幅をはみ出さずに適切に省略（ellipsis）またはツールチップ表示させる。
- **対象スコープ**: `sf-markdown-editor`（`markdownChecklistPanel` UIレイアウト）

### 2. 設定したToDoのアラーム設定（リマインダー通知連動）✅ 対応済み（2026-08-19、Task 作成時のみ）

- **対応内容**: `markdownChecklistPanel` の Task 作成エリア（未ToDo化行）に、リマインダーの利用On/Offトグル（`lightning-input type="toggle"`）とリマインド日時ピッカー（`lightning-input type="datetime"`）を追加した。トグルをOnにすると `MarkdownTaskSync.createTaskForCheckbox` の `isReminderSet` / `reminderDateTime` 引数経由で Task の標準リマインダー機能（`IsReminderSet` / `ReminderDateTime`）が設定される。
  - **既定値（自動初期値）の考え方**: リマインド日時は「期日（`ActivityDate`）当日の 09:00（ローカル時刻）」をデフォルトとした。理由は次の2点。
    1. 期日の「○時間前」のような相対プリセットは、期日に時刻の概念がない（`ActivityDate` は日付のみ）ため、基準時刻をどこに置くか別途決める必要があり、結局「当日の何時」という絶対時刻の決定に帰着する。
    2. hk.issue 運用は日次の定例処理・確認作業を JST 9:00 起点で回している（例: `retrieve.yml` の日次メタデータ取得は JST 9:00 実行）。同じ「業務開始時刻」に合わせておくことで、当日の朝一番に思い出せるという体感的にも分かりやすい基準になる。
  - トグルOn後に期日を変更すると、ユーザーがリマインド日時を手動編集していない限り、既定値も追従して再計算される（手動編集後は上書きしない）。期日が未入力の間はトグルOnにしても既定値は入らず、ユーザーが直接時刻を指定する運用になる。
- **未対応（将来検討）**: 作成済み Task 側（`markdownTaskPreview` のインライン編集）でのリマインダー変更は、`editableFieldsConfig` に `IsReminderSet,ReminderDateTime` を含めることで App Builder 設定のみで対応可能（コンポーネント自体の追加改修は不要）。カスタム通知・Flow連携によるアラーム自動化は未着手。
- **ユーザーの声**:
  > 「設定したToDoのアラーム設定がされるといいですね。」
- **課題・背景**:
  - `markdownChecklistPanel` からチェックボックス項目を Task 化して管理する際、期日前の通知・リマインダー（アラーム）が設定されていないと、期日超過や対応漏れが発生しやすい。
  - Salesforce 標準の `Task` オブジェクトにはリマインダー通知機能（`IsReminderSet`, `ReminderDateTime`）が備わっているが、`markdownTaskPreview` 側からこれらを直接設定・連動できると利便性が大きく向上する。
- **対象スコープ**: `sf-markdown-editor`（`markdownChecklistPanel` UI設定項目・`MarkdownTaskSync` 更新連携）

### 3. 1レコードに対する複数Markdownページの管理（子レコード・ドロップダウン切替）

- **ユーザーの声**:
  > 「課題のようなオブジェクトでは、１レコードに複数のMarkdownページを配置できるのも一案と思いました。（別オブジェクトが必要そうですね。作成ボタンにより、ページ（レコード）を作る。レコードをドロップダウンリストにより切り替えることでMarkdownの表示内容を変える。）」
- **課題・背景**:
  - 課題（`TaskMng__c` 等）やプロジェクト管理において、1つのレコード内に要件定義・技術仕様・議事録・検証結果など、複数の独立したMarkdownドキュメントを整理・保持したいユースケースがある。
  - 単一の長文テキスト項目（`Markdown__c`）では、内容が長大化して目的の情報を見つけにくくなる。
- **改善案・対応方針**:
  - **子オブジェクトによるページ管理アーキテクチャ**:
    - ページ管理用の子カスタムオブジェクト（例: `TaskMarkdownPage__c`、項目: `Title__c`, `Content__c`, `SortOrder__c`, `Category__c` 等）を作成。
    - 親レコード画面上に「新規ページ作成」ボタンを配置し、ワンクリックで新しいページレコードを生成。
  - **UIコンポーネントの提供**:
    - ドロップダウンリスト（Select / Combobox）やタブ形式でページを即座に切り替え、選択されたページのMarkdown内容を表示・編集するコンポーネントを設計。
- **対象スコープ**: `sf-markdown-editor`（マルチページ対応コンポーネントの提供）、`hk.issue`（メタデータ・オブジェクト設計）

### 4. 画像埋め込み対応とストレージ容量・保存先考慮

- **ユーザーの声**:
  > 「たしかに、画像埋め込めるといいですね。置くならば、画像を置くストレージも考えないと・・・というところでしょうか。」
- **課題・背景**:
  - Markdownやタスク説明への画像埋め込み（スクリーンショット貼付、設計図、UIモックアップ等）の需要は非常に高い。
  - 一方で、Salesforce 組織のファイルストレージ容量（`ContentVersion` / `ContentDocument`）は上限があり、画像を無制限に Base64 や標準ファイルとして保存し続けるとストレージ枯渇やコスト増のリスクがある。
- **改善案・対応方針**:
  - **Salesforce標準ストレージ（ContentVersion）の活用と最適化**:
    - `sf-markdown-editor` では既に `MarkdownImageHandler.cls` による Data URI → `ContentVersion` 変換の仕組みが提供されている。
    - 画像アップロード時の自動リサイズ・圧縮（JPEG/WebP変換等）をフロントエンドで事前処理し、ファイルサイズを最小化する。
  - **外部ストレージ連携の検討**:
    - 大容量・大量の画像保存に対応するため、Box / AWS S3 / Google Drive / Azure Blob などの外部ストレージと連携するプラグイン／拡張インターフェースの検討。
    - ストレージ使用量の監視や定期的なクリーンアップ運用ルールの策定。
- **対象スコープ**: `sf-markdown-editor`、インフラ・ストレージ運用設計
